# Техническое задание на разработку программного продукта для планирования встреч

## Команда: нет минусов, одни си плюс плюсы

### 1. Общие описание
Необходимо разработать программный продукт для планирования встреч сотрудников внутри компании. Система состоит из клиентского мобильного приложения и серверной части.

### 2. Клиентская часть (Android-приложение)
Клиентом является **Android-приложение**, которое должно быть реализовано на **Kotlin** или **Java** с использованием **адаптивной верстки**.

Приложение должно предоставлять интуитивно понятный интерфейс, в котором реализован следующий функционал:

*   **Регистрация и авторизация** сотрудника.
*   **Настройка личного профиля**.
*   **Создание встречи** с возможностью приглашения других сотрудников. Приглашенные сотрудники должны иметь возможность дать бинарный ответ (**принял** / **не принял**).
*   **Просмотр списка активных приглашений** на встречи с возможностью дать ответ о возможности посещения.
*   **Просмотр собственного расписания встреч** в разрезе дня, недели и месяца.

**Важное условие:** временные слоты для встреч разбиты строго по часам. Например, можно создать встречу на 9:00–10:00, но создание встречи на 9:10, 9:05 и т.д. — невозможно.

### 3. Серверная часть
Сервер представляет собой **микросервис на Spring Boot**, работающий с СУБД **PostgreSQL** или **H2**.

Серверное приложение должно:
*   Предоставлять API, необходимый для полноценной работы мобильного приложения.
*   Осуществлять все основные операции с данными в базе через **Spring Data JPA**.
*   Использовать **Liquibase** для создания схемы базы данных и ее предзаполнения.


## User Story

### Регистрация и авторизация
- **Как пользователь**, я хочу зарегистрироваться, чтобы получить доступ к приложению;
- **Как пользователь**, я хочу войти в приложение, чтобы получить доступ к своему аккаунту;
- **Как пользователь**, я хочу, чтобы мои данные для входа сохранялись, чтобы не вводить их повторно при каждом запуске приложения.

### Настройка личного профиля
- **Как пользователь**, я хочу менять свои личные данные (имя, должность, отдел, аватар, контактные данные), чтобы коллеги могли меня узнать.

### Создание встреч
- **Как пользователь**, я хочу создать новую встречу, чтобы обсудить что-нибудь.
- **Как организатор встречи**, я хочу пригласить на неё других пользователей, чтобы они пришли на встречу.
- **Как организатор встречи**, я хочу видеть статус (принял/отклонил) от всех приглашенных на мою встречу, чтобы понимать, кто сможет присутствовать.

### Управление встречами
- **Как пользователь**, я хочу видеть список всех активных приглашений на встречи, чтобы принять решение об участии.
- **Как приглашенный пользователь**, я хочу дать ответ (принять/отклонить) на приглашение, чтобы организатор знал о моем решении.
- **Как приглашенный пользователь**, я хочу видеть предупреждение о том, что встреча накладывается на другие, чтобы я мог выбрать более важную встречу **(НЕ ОБЯЗАТЕЛЬНО)**

### Просмотр собственного расписания встреч
- **Как пользователь**, я хочу видеть своё расписание на день, чтобы знать сегодняшние встречи.
- **Как пользователь**, я хочу видеть своё расписание на неделю, чтобы понимать свою загруженность в ближайшие дни.
- **Как пользователь**, я хочу видеть своё расписание на месяц, чтобы видеть занятые встречами даты.

## Use Cases

### Регистрация / Авторизация

* **RegisterUseCase**
  * **Цель:** создание аккаунта
  * **Участники:** незарегистрированный пользователь
  * **Основной поток:**
    * Ввод имени, фамилии, email, пароля и повторение пароля;
    * Нажал на кнопку "Создать профиль";
    * Приложение валидирует данные (имя и фамилия не пустые, email соответствует формату, пароль >= 8 символам);
    * Отправляет запрос на сервер (`POST /auth/register`);
    * Сервер проверяет данные на корректность, сохраняет пользователя и отправляет `201`;
    * Приложение сохраняет учётные данные и открывает главный экран.
  * **Альтернативный поток:**
    * Поля не прошли валидацию (в приложении) -> поля подсвечиваются красным, отображаются соответствующие ошибки;
    * Поля не прошли валидацию (на сервере) -> возвращается код `400` -> отображение ошибки через Toast (Snackbar);
    * Email занят -> возвращается код `409` -> поле подсвечиваются красным, отображается ошибка "email занят";
* **LoginUseCase**
  * **Цель:** вход в аккаунт
  * **Участники:** неавторизованный пользователь
  * **Предусловия:** создан аккаунт
  * **Основной поток:**
    * Ввод email, пароля;
    * Нажал на кнопку "Войти";
    * Приложение валидирует данные (email соответствует формату, пароль >= 8 символам);
    * Отправляет запрос на сервер (`GET /auth/login`);
    * Сервер проверяет данные на корректность и отправляет `200`;
    * Приложение сохраняет учётные данные и открывает главный экран.
  * **Альтернативный поток:**
    * Поля не прошли валидацию (в приложении) -> поля подсвечиваются красным, отображаются соответствующие ошибки;
    * Email или пароль неправильные -> возвращается код `404` -> отображается ошибка "Email или пароль неправильные".
* **AuthorizeUseCase**
    * **Цель:** автоматически авторизовать пользователя при запуске приложения
    * **Участники:** система
    * **Предусловия:** в локальном хранилище есть сохраненные учетные данные
    * **Триггер:** вход в приложение
    * **Основной поток:**
      * Система отправляет данные на сервер (`GET /auth/login`);
      * Сервер проверяет данные на корректность и отправляет `200`;
      * Приложение открывает главный экран.
    * **Альтернативный поток:**
      * Email или пароль неправильные -> возвращается код `404` -> отображается ошибка "Email или пароль неправильные".

### Управление личным профилем
* **UpdateProfileUseCase**
  * **Цель:** обновить информацию в профиле
  * **Участники:** пользователь
  * **Предусловия:** пользователь авторизован
  * **Триггер:** нажатие кнопки "Редактировать"
  * **Основной поток:**
    * Ввод новых данных (имя, фамилия, должность, контакты);
    * Система отправляет данные на сервер (`POST /users/{id}`);
    * Сервер проверяет и обновляет данные, отправляет `200`;
    * Приложение переходит на экран профиля.
  * **Альтернативный поток:**
    * Поля не прошли валидацию (в приложении) -> поля подсвечиваются красным, отображаются соответствующие ошибки;
    * Поля не прошли валидацию (на сервере) -> возвращается код `400` -> отображение ошибки через Toast (Snackbar);
    * Пользователь не имеет доступа к изменению этих данных -> возвращается код `401` -> отображается ошибка и возвращается на экран профиля (**Обработка этой ошибки может подождать, тк обычно её быть не должно**);
    * Пользователь не найден -> возвращается код `404` -> отображается ошибка и возвращается на экран профиля (**Обработка этой ошибки может подождать, тк обычно её быть не должно**).

### Управление встречами
* **CreateMeetingUseCase**
  * **Цель:** создать новую встречу и разослать приглашения
  * **Участники:** пользователь
  * **Предусловия:** пользователь авторизован
  * **Триггер:** нажатие кнопки "Создать встречу"
  * **Основной поток:**
    * Ввод названия (темы) и описание встречи, выбор даты и часового слота;
    * Нажатие кнопки "Создать";
    * Переход на следующий экран с поисковой строкой и списком пользователей, которых можно выбрать (выбранные пользователи отображаются сверху в виде chip-ов) (**Можно упростить**)
    * Выбор пользователей;
    * Система отправляет данные встречи, id создателя и id пользователей на сервер (`POST /booking/create`);
    * Сервер создаёт встречу, приглашения для пользователей и отправляет `200`;
    * Приложение открывает экран просмотра созданной встречи.
  * **Альтернативный поток:**
    * Если тема пустая или даты и время не выбраны -> приложение требует их заполнить;
    * ...
* **GetInvitationsUseCase**
  * **Цель:** получение списка непросмотренных (неотвеченных) приглашений для пользователя
  * **Участники:** пользователь
  * **Предусловия:** пользователь авторизован
  * **Триггер:** открытие раздела "Приглашения"
  * **Основной поток:**
    * Система отправляет id пользователя (`GET /users/invitations/{id}`);
    * Сервер возвращает список приглашений и статус `200`;
    * Приложение отображает список.
  * **Альтернативный поток:**
    * ...
* **RespondToInvitationUseCase**
    * **Цель:**  отправить ответ на приглашение (принять/отклонить)
    * **Участники:** пользователь
    * **Предусловия:** пользователь авторизован и есть активные приглашения
    * **Триггер:** нажатие кнопки "Принять" или "Отклонить" на конкретном приглашении
    * **Основной поток:**
      * Система отправляет id пользователя, id приглашения и выбор (`true/false`) (`POST /users/invitations/`)
      * Сервер обновляет статус пользователя и расписание пользователя возвращает `200`;
      * Приглашение пропадает из списка активных.
    * **Альтернативный поток:**
      * ...
* **ViewScheduleUseCase**
  * **Цель:** отобразить расписание встреч пользователя за выбранный период
  * **Участники:** пользователь
  * **Предусловия:** пользователь авторизован
  * **Триггер:** пользователь открывает раздел "Расписание" и выбирает период (день/неделя/месяц)
  * **Основной поток:**
    * Система запрашивает список встреч за этот период (`GET /users/{id}/schedule/day (/week, /month)`)
    * Сервер формирует ответ и отправляет его со статусом `200`;
    * Приложение отображает список встреч (в виде списка для дня и недели, в виде календаря для месяца;
  * **Альтернативный поток:**
    * За выбранный период нет встреч -> система отображает экран заглушку.
